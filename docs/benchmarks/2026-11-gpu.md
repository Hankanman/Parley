# GPU benchmarks, November 2026

Measured on starrunner: AMD Ryzen 9 5950X, RTX 3080 Ti (12 GB), NVIDIA driver
with Vulkan 1.4, Fedora 45. The scripts are in `scripts/bench/`.

They back three changes:

- The built-in AI helper no longer reloads the model when the context size
  changes.
- VRAM detection now works on Vulkan, and a full offload now offloads every
  layer.
- CUDA builds are dropped in favour of Vulkan.

## 1. Model reloads (`llama_reload.py`)

The test sends eight requests with the context sizes from a real summary
(32k, 16k, 8k, 8k, 16k, 16k, 8k, 16k). The prompts are short, so the timing
is mostly load overhead. Figures are the median of 3 runs.

| | Before | After | Change |
|---|---|---|---|
| CPU, gemma3:1b | 6.46 s | 4.88 s | −24% |
| CPU, gemma3:4b | 24.00 s | 17.35 s | −28% |
| CUDA, gemma3:1b | 3.48 s | ~1.4 s* | ~−60% |
| CUDA, gemma3:4b | 7.74 s | ~4.9 s* | ~−37% |

Each reload cost about 0.3 s (1B) and 1.3 s (4B) on the CPU. On the GPU, a
request that triggered a reload took 0.48 s against 0.08 s without (1B), and
0.96 s against 0.40 s (4B).

\* These are estimates, because the CUDA 13.5 toolchain couldn't build the
new helper. They use the old helper's request time when there was no reload.

## 2. Built-in AI on the GPU (`llama_throughput.py`)

The test is a summary-style prompt with a greedy 400-token answer, timed
after warm-up. Times are total seconds, with the prompt-processing time in
brackets.

| 3080 Ti | gemma3:1b, ~3k / ~12k-token prompt | gemma3:4b, ~3k / ~12k |
|---|---|---|
| CUDA, old helper | 1.61 (0.22) / 2.29 (0.74) | 8.08 (1.03) / 12.17 (3.54) |
| Vulkan, old helper (0.5.3 release) | 1.58 (0.22) / 6.03 (1.46) | 15.03 (1.54) / 29.60 (6.24) |
| **Vulkan, new helper** | **1.54 (0.22) / 2.17 (0.69)** | **3.19 (0.65) / 5.25 (2.07)** |

The old helper only detected VRAM on CUDA builds. Vulkan builds, which is
what every release ships, assumed 4 GB and offloaded only part of the model.
The old helper also capped a "full" offload at a layer count it guessed from
the file size, which left 6 of gemma3:4b's 34 layers on the CPU, even on
CUDA. With both fixed, Vulkan matches CUDA on the 1B model and is 2.5–5.6×
faster than the 0.5.3 release on the 4B model.

## 3. Whisper, CUDA vs Vulkan (`whisper_bench.cpp`)

These runs used the same whisper.cpp version Parley ships, on 5 minutes of a
real meeting recording. The settings match Parley's: beam search with 5
beams for the final text, greedy decoding for partial previews, and flash
attention on CUDA only.

| 3080 Ti | 8 s segment, final (median / p90) | Partial preview | 5-minute file |
|---|---|---|---|
| large-v3-turbo, CUDA | 0.16 / 0.22 s | 0.11 s | 4.4 s (69× real time) |
| large-v3-turbo, Vulkan | 0.21 / 0.27 s | 0.16 s | 11.1 s (27×) |
| large-v3, CUDA | 0.30 / 0.39 s | 0.23 s | 12.8 s (23×) |
| large-v3, Vulkan | 0.55 / 0.97 s | 0.36 s | 24.8 s (12×) |

Live transcription runs far faster than real time on either backend.
Whole-file jobs (import, retranscription, refinement after a recording) take
about 2–2.5× as long on Vulkan. Turning flash attention on for Vulkan made
partial previews 18–33% faster and whole files 10–15% faster, but nearly
doubled the p90 of turbo final decodes, so it stays off.

## Reproducing

```bash
# Built-in AI: helper binary, GGUF model, number of runs
python3 scripts/bench/llama_reload.py target/release/llama-helper ~/.local/share/io.github.hankanman.Parley/models/summary/gemma-3-4b-it-Q4_K_M.gguf 3
python3 scripts/bench/llama_throughput.py target/release/llama-helper <model.gguf>

# Whisper: build whisper.cpp (GGML_VULKAN=ON or GGML_CUDA=ON) and link
# whisper_bench.cpp against it. Input is raw 16 kHz mono f32 audio:
ffmpeg -t 300 -i meeting.mp4 -ac 1 -ar 16000 -f f32le audio.f32
./whisper_bench ggml-large-v3-turbo-q5_0.bin audio.f32 <flash_attn 0|1>
```
